Start here: Node & Vault

Use Node to receive, prepare payments and broadcast. Use Vault to keep the signing keys offline and approve spending. This walkthrough starts with your installed Node and a signing wallet created and backed up on Bitcoin Core Vault. The Vault Guide covers that first wallet and its separate Core/GPG passphrases.

The online Node stores a watch-only wallet: public address information, labels and transaction history, without the private keys. A PSBT (Partially Signed Bitcoin Transaction) carries an unsigned payment and supporting information to Vault, and carries the signatures back. No signing wallet or signing secret needs to come online.

1. Install and connect Node

Boot the Node installation USB, choose the keyboard and target disk, and review the selection. Installation erases that disk. Please disconnect valuable backup drives before installing. After installation, restart without the installation USB. Use Network Status to connect to Wi-Fi, or connect an Ethernet cable.

2. Choose how to protect access to this computer

A watch-only wallet is stored persistently on Node. Someone using its unlocked desktop can inspect your financial history. Open Settings → Login Password to set an optional password for the next login. This prevents ordinary automatic access to the desktop; it does not encrypt the disk or protect an already-open session. Read Device privacy & login before leaving the device unattended.

3. Choose block storage before downloading

Open Bitcoin Core. In its first-start window, choose the intended data location and whether to limit block storage. Pruning retains less old block data after validation. Choose a target that leaves space for chainstate, indexes and maintenance, not the entire free disk. See Storage & pruning for a worked example. Import an existing trusted Node blockchain backup first if you intend to reuse one.

4. Export the public wallet from Vault

On offline Vault, select your signing wallet in Bitcoin Core and choose File → Export watch-only wallet. Save it as watch-only.dat in Private Workspace, then use Files to copy that public export to your transfer USB. Do not bring the original signing wallet.dat, a decrypted signing backup, or the Core/GPG passphrases protecting the Vault signing backup to Node.

5. Restore the public copy into Node's Core

Connect the transfer USB. In Bitcoin Core choose File → Restore Wallet, select watch-only.dat and give the restored wallet a clear new name. You can select it from the USB sidebar or first copy it to PSBT Transfer Folder. If the public export itself is GPG-encrypted, use Decrypt Files and select the recovered public .dat in Private Workspace. Core creates a persistent public wallet on Node's disk; the transfer copy remains temporary if it is in RAM.

6. Finish synchronization and wallet scanning

Let Core validate the blockchain and scan the wallet's transactions. These are separate operations. Resolve warnings about missing pruned history; an unfinished scan is not a reliable balance. Check that you restored a watch-only wallet and that it corresponds to the intended Vault wallet and Bitcoin network.

7. Create a receiving address on Node

Select the watch-only wallet, open Receive, add a useful label and choose Create new receiving address. Share the resulting address or QR code with the sender. Independently confirm that the address belongs to the corresponding Vault wallet before a significant deposit. Address requests advance a wallet's address index, so compare the same address/index rather than assuming that two separately generated requests must match. Receiving bitcoin does not require Vault to be powered on.

8. Back up your online setup

Open Settings → Backup and Restore. Save the watch-only collection and Node configuration to separate backup media. Node configuration already includes supported Core settings. A blockchain backup is optional: it saves download/validation time after a disk failure or move to another computer, but is not a signing-wallet backup. Keep another copy and do not rely on a backup stored only on this computer's own disk.

9. Prepare an unsigned payment

With Core synchronized and the watch-only wallet selected, open Send. Enter the recipient's address and amount, choose the fee and review the payment. Use Create Unsigned to make a PSBT; this does not spend or broadcast anything. Save it as an identifiable .psbt file in PSBT Transfer Folder or directly on a writable transfer USB.

10. Move the PSBT to Vault

If saved in a RAM folder, use Files to copy it to the USB before restarting Node. Finish writes and eject/unmount the USB. On Vault, use Files to copy the PSBT into Private Workspace and open Bitcoin Core → File → Load PSBT from file. Use the matching signing wallet.

11. Review and sign offline

In Vault, independently check the recipient address, amount, fee and change returned to your own wallet. Enter the Core wallet passphrase only there, when required, and select Sign Tx. Save the signed PSBT in Vault's Private Workspace, then copy it to the transfer USB with Files. Vault's Core USB view is read-only. Vault does not broadcast the transaction.

12. Bring the signed transaction back and broadcast

On Node, choose File → Load PSBT from file and open the returned signed PSBT. Check that it is the payment you approved and that signing is complete. Choose Broadcast Tx only when ready. The synchronized online Node sends it to Bitcoin peers. Watch the transaction in Core: broadcast is not a block confirmation, and a transaction ID alone is not proof of successful relay.

13. Save necessary files before restarting

The installed blockchain, restored watch-only wallets and Node settings persist. Private Workspace and PSBT Transfer Folder do not: they are RAM-only and clear at shutdown/restart or power loss. Save any unfinished PSBTs, recovered exports and notes you still need. Use normal Restart/Shut Down so Core can close cleanly.

The remaining chapters explain these steps and the applications that support them. Keep the original signing-wallet backup and its redundant, separately stored secrets under your Vault recovery plan; Node's public backups do not replace them.

Device privacy & login

Watch-only does not mean publicly readable. It means the wallet lacks private spending keys. The public descriptors, address book, balances and transaction history stored on this Node can still reveal your finances.

What someone with access can see

Someone at an unlocked Node desktop can open Core and inspect loaded wallets. Closing a wallet window, stopping Core or restarting does not erase the persistent watch-only database. A person who can read the disk directly may copy the database and examine it on another computer. Screenshots, diagnostic output, watch-only exports and unencrypted wallet collections can reveal similar information.

Without the Vault signing keys, the watch-only copy cannot independently sign a payment. However, a compromised online computer can propose false recipients, amounts or change outputs, or show a misleading receiving address. Independent checks on Vault remain part of the workflow.

Optional desktop login password

Open Settings → Login Password.

Enter and repeat a password, then choose Set password. Choose a secret that is practical to use and not easily guessed. A random KeePassXC phrase is one option.

At the next start or restart, enter it on the Bitcoin Core Node login screen and press Enter. The username is fixed; you do not create another account.

Change password replaces the secret; Remove password returns to automatic login at the next login.

These settings do not lock the current session. Anyone already using that desktop has its normal controls, including password settings. Shut down normally before leaving an unattended device in a place where others can use it. The current session must not be treated as protected just because you set a password.

This login password is not disk encryption. It provides an ordinary login barrier, not protection against booting another operating system, removing the disk, an administrator or a compromised running system. Keep physical access controlled. The installer does not add full-disk encryption. Encrypting an exported backup protects that export only, not Core's active watch-only database.

Different passwords have different jobs

The login password is for entering this Node desktop, not for each routine operation. Built-in backups, restores, updates and settings retain their confirmations but do not repeatedly request it. A GPG passphrase opens a particular encrypted backup. The Core signing-wallet passphrase belongs on offline Vault. Do not reuse the Vault secrets as the Node login password. Advanced Terminal sudo commands retain normal Linux authentication.

The Node configuration backup intentionally excludes the login password and account identity. Set a new login password on a replacement computer. Back up public wallet data privately; keep any encryption passphrase separately recoverable. Treat this as a dedicated Node rather than a computer for opening unrelated attachments, browsing or installing arbitrary software.

Storage & pruning

Choose how much old block history you keep, not how much checking Core performs. An archival node retains the historical blocks. A pruned node validates blocks under the same rules, then removes older block and undo files to stay near a storage target. Pruning reduces retained storage; it does not eliminate the initial download and validation work.

What the storage bar measures

Home's Blockchain storage bar shows percentage full and remaining usable space for blockchain data. Its capacity is allocated blocks, chainstate and indexes + free space available to Core. It excludes space already occupied by Debian, installed programs, wallets, other files and filesystem reservations.

For example, 30 GiB used by blockchain data plus 60 GiB free gives 90 GiB capacity and 33.3% full. This is not a separate reserved partition. Saving unrelated files or installing updates can reduce the available space. The usage estimate refreshes periodically; it is not a promise about how large the blockchain will be when synchronization finishes.

Set the target in Bitcoin Core

Read the free/capacity figures for the actual disk where Core stores its data, not the capacity printed on the computer's packaging.

In Core's first-start storage window, or later under Bitcoin Core → Settings → Options, enable the option to limit/prune block storage and enter the intended target.

Use the unit displayed beside that field. Apply the setting and restart Core if it asks.

Monitor the storage bar during synchronization and afterwards. Leave free space for database growth and maintenance rather than aiming for 100% full.

A practical budget

Block-file target ≤ usable blockchain capacity − chainstate/index allowance − free-space reserve. Chainstate is Core's database of currently unspent outputs; it remains needed even after old blocks are deleted. Indexes help Core find its data. These are not all controlled by the block pruning target.

Illustrative example, not a measurement of today's chainstate: suppose the bar gives 90 GiB of usable capacity. Allow 20 GiB for chainstate and related indexes and leave another 20 GiB free. That leaves a ceiling of 50 GiB for retained block files; choosing less, such as 40 GiB, adds room. Replace those allowances with the actual usage and expected growth of your Node. An allowance that is adequate now may be too small later.

Units matter: 1 GiB = 1,024 MiB ≈ 1.074 GB. A 40 GiB target is 40,960 MiB, approximately 43 GB. Use the field's displayed unit; entering 40 in a field labelled GB is a slightly smaller target than 40 GiB. Advanced bitcoin.conf settings use prune in MiB. Do not paste a GiB number directly into that configuration option.

A larger target retains more recent history and gives more room for wallet rescans. It does not guarantee a fixed number of days or months: block sizes and transaction activity vary. A smaller target suits a smaller disk but requires more care with old or rarely opened wallets. No disk-size recommendation is permanent.

Plan watch-only imports before old history disappears

Restore your public wallet early and keep it loaded while Core synchronizes and prunes. A rescan looks through older blocks for that wallet's transactions. If needed blocks have already been removed, Core cannot reconstruct the missing history from a public descriptor alone. A pruned backup contains only retained blocks; copying it cannot restore blocks already deleted.

For an old wallet or one left unloaded for a long time, recover a trusted copy with the needed history or use an archival node/re-download as required by Core. Do not invent a newer wallet creation date just to dismiss a warning. Wait until validation and wallet scanning have finished before trusting a balance.

Changing your choice later

Reducing the target may delete more old blocks. Increasing it retains more future blocks but does not automatically fetch all previously pruned history. Disabling pruning to return to archival operation can require downloading and rebuilding the complete history. Also leave extra temporary space when importing a blockchain backup: the current copy is kept until the incoming copy passes its restore checks.

Technical source: Bitcoin Core's own -prune help in src/init.cpp and the pruning tests in test/functional/feature_pruning.py (github.com/bitcoin/bitcoin). The Node capacity formula is described above; it does not change Core's pruning rules.

Bitcoin Core

Bitcoin Core is the application that validates the blockchain, stores the public wallet, creates receiving addresses, prepares unsigned PSBTs and broadcasts the transactions signed on Vault. Use its ordinary wallet menus for those jobs; Node's Home and Settings provide the surrounding system tools.

Start and control Core

Open Bitcoin Core on Home to start it or return to its window. Use the wallet selector when more than one wallet is open. File → Open Wallet opens an existing wallet, and File → Close Wallet unloads one without deleting its database. Closing a window and ending the Core process are not always the same operation; use File → Exit or the Node Core-status controls to stop it cleanly.

The indicator beside the clock describes Bitcoin peer connections, not merely Wi-Fi association. It opens details and controls. Pause sync temporarily disconnects peers; Resume sync reconnects. Stop Bitcoin Core closes Core so it can finish saving. Restart there restarts Core, not this computer.

What the Home status area means

The text and visible meters are centered between the launchers and the Debian logo. The upper meter follows Core's validation-progress estimate in 100 segments. The lower meter shows blockchain storage percentage full and available capacity. A stopped/error message occupies the same centered area without empty bars. A changing percentage is not a promised finishing time.

Keep signing separate

The intended Node/Vault setup uses only public watch-only wallets here. Creating a signing wallet in online Core is possible, but it is a different arrangement: its private keys would be on the online device. Do not restore the Vault signing database here merely to make a PSBT easier to use. Node's Watch-only wallets backup intentionally skips signing wallets.

Delete a local wallet deliberately

First keep any public wallet/label backup you need. Close the selected wallets in Core. In Files → Core → wallets, select their folders, right-click Permanently Delete Bitcoin Core Wallets…, review and use the red Permanently Delete button. Ctrl-click selects several. Loaded or invalid selections are refused. The batch stops Core once and restarts it after success; it does not delete the blockchain or unrelated wallets.

Deletion and overwriting are best effort, especially on SSDs and USB flash. Older copies or filesystem history may remain. Deleting a watch-only copy does not delete Bitcoin or the offline signing wallet; deleting the only signing wallet without a usable backup can lose access to funds. Keep the distinction explicit.

Synchronization

Synchronization brings this Node up to date with the Bitcoin network. Core downloads blocks and checks them; its initial work depends on the disk, connection and processor. Keep the data disk connected and use normal shutdown rather than cutting power.

Validation and wallet scanning are separate

Blockchain validation checks the chain against Bitcoin's rules. Wallet scanning identifies transactions belonging to a particular wallet. Restoring a public wallet after the chain is downloaded may still require a scan. Wait for both before relying on the balance or preparing a spend. A temporary zero balance is not proof of no funds.

At first Core may download/check headers, the small block summaries, before the validation meter moves noticeably. Look at the header count, block count and peer connections rather than treating a slow percentage as a failure. Settings → Bitcoin Core Status → Show technical details opens a separate diagnostic window.

Continue after an interruption

After a clean stop, the installed Node keeps the completed chain data and can continue on the next start. If the selected data disk is missing, reconnect it instead of choosing a new empty directory by accident. If Core reports corruption, preserve the existing data and investigate the actual error.

Read Storage & pruning before choosing a retention target, especially for old wallet imports. Use Blockchain backup to move an already synchronized trusted copy to another Node. Even after importing it, Core must catch up with newer blocks; a copied tip is not today's network tip forever.

Watch-only wallets

A native watch-only export contains public descriptors, receiving/change-address state, labels, address-book entries and recorded transactions, without private keys. Descriptors are the instructions Core uses to recognize and derive the wallet's addresses. This lets Node follow the same wallet while Vault retains signing authority.

Import the file exported by Vault

On Vault, choose Bitcoin Core → File → Export watch-only wallet from the intended signing wallet. Save the public watch-only.dat in Private Workspace and copy it to a USB with Files.

On Node, open Core and select File → Restore Wallet. Use the USB sidebar or a public copy in PSBT Transfer Folder. Give the wallet a new name.

For a GPG-encrypted public export, use Decrypt Files first and restore the recovered .dat from Private Workspace. Do not decrypt a signing backup on Node.

Wait for Core's scan and resolve pruning warnings. Compare public address information with the corresponding Vault wallet and confirm the Bitcoin network.

Core's restore copies the public database into persistent wallet storage. Removing the transfer USB or clearing Private Workspace does not remove that active wallet.

Use the correct import path

A single watch-only.dat from Vault belongs in Core → File → Restore Wallet. A .json/.gpg collection created by Node's watch-only backup belongs in Backup and Restore → Watch-only wallets → Restore. The formats are intentionally different; no manual descriptor JSON editing is needed for the native .dat flow.

When Node detects a loaded supported public-only wallet, Watch-Only Wallets and PSBT Transfer Folder appear together on Home. Closing the wallet is not deletion: reopen it with File → Open Wallet. Keep it loaded during pruning so it can stay caught up before old blocks disappear.

Public information can reveal balances and transaction history. Use the optional login password and physical access precautions described in Device privacy & login. Protect public exports and backups too; watch-only does not make them nonsensitive.

Technical source: Bitcoin Core's offline-signing-tutorial.md and release-notes-32.0.md under github.com/bitcoin/bitcoin/doc describe exportwatchonlywallet and restorewallet. This Guide uses the corresponding GUI actions in the bundled Core.

Receiving bitcoin

Once the correct watch-only wallet is restored, Node can generate receiving addresses without asking Vault to sign anything. The private keys remain offline. Vault does not need to be running to receive a payment.

Open Bitcoin Core on Node and select the intended watch-only wallet.

Open Receive. Add a label that will help identify the payment later. An optional requested amount is information for the payer, not a restriction on what that address can receive.

Choose Create new receiving address. Copy the displayed address or show the QR code.

Before a significant deposit, independently confirm the address belongs to your corresponding Vault wallet and the correct Bitcoin network. Checking only two displays on the online computer is not an independent check.

Share the address with the sender. Use a fresh receiving address for a new payment when practical to reduce simple address reuse.

Wait for the payment to appear and for confirmations. Keep Core synchronized and the wallet scan complete when checking status.

Compare the same address, not different requests

Both wallet copies can generate a sequence of addresses. Creating more requests on one side advances its next-address index, so the next request on Vault is not necessarily the same as the latest request on Node. For the initial pairing, compare corresponding addresses at the same index before making extra requests. For an address not already visible in Vault's address information, resolve that match using Core's wallet/address tools rather than accepting a visually similar address or a familiar wallet name.

A receiving address is public but can link payments to you. Do not publish a whole watch-only export merely to request payment; share only the address needed. Labels/history are local useful records, so keep a watch-only backup after important changes. Backing up Node never substitutes for recovering the offline signing wallet.

PSBT transactions

Node prepares → Vault reviews and signs → Node broadcasts. A PSBT is a Partially Signed Bitcoin Transaction: it carries transaction details and supporting public data so the offline wallet can sign without connecting to the network. An unsigned PSBT has no authority to spend. A fully signed payment may be broadcast by anyone holding it, so handle the returned file deliberately.

1. Prepare on the online Node

Wait for blockchain synchronization and wallet scanning. Select the correct watch-only wallet in Core.

In Send, enter the recipient's address and amount. Review the fee; Coin Control is available when you want to choose specific outputs.

Use Create Unsigned rather than expecting Node to sign. Save the .psbt to PSBT Transfer Folder or directly to writable USB. A filename such as payment-unsigned.psbt helps distinguish it from the returned file.

If the file is in a RAM working folder, use Files to copy it to the transfer USB. Finish writing and eject/unmount safely.

2. Review and sign on offline Vault

Copy the unsigned PSBT to Vault's Private Workspace. Open the corresponding signing wallet and choose File → Load PSBT from file.

Independently verify every recipient, amount, fee and change output. Change is the unused part of the selected inputs returning to your own wallet.

When satisfied, unlock the wallet with its Core passphrase if required and choose Sign Tx.

Save the signed PSBT in Vault's Private Workspace. Then copy it to USB with Files; Vault's Core USB view itself is read-only. Keep the signing wallet and its secrets offline.

3. Return to Node and broadcast

Connect the USB to Node. Choose File → Load PSBT from file in Bitcoin Core and select the signed file. A RAM copy is optional.

Recheck that the intended transaction is complete and matches the payment approved in Vault. An incomplete PSBT cannot be broadcast as a complete transaction.

Choose Broadcast Tx. Node sends the signed transaction to its peers using the configured route.

Inspect the transaction in Core afterwards. Broadcast does not guarantee inclusion in a block; confirmations arrive after miners include it. A fee estimate is not a guarantee of confirmation time.

There is no extra custom Node transaction app or proprietary proposal file in this flow. Core handles the PSBT and transaction. Do not select an original signing wallet backup when asked for a PSBT.

Keep unfinished payment files you still need outside RAM before shutdown. A PSBT is not your wallet recovery backup. If private broadcast is enabled and fails, inspect that route rather than silently switching to a different privacy setting.

Technical source: Bitcoin Core doc/psbt.md and doc/offline-signing-tutorial.md (github.com/bitcoin/bitcoin). The standard separates transaction creation, signing and broadcast; the GUI combines the intermediate PSBT processing steps.

Backups & recovery

Start at Settings → Backup and Restore. A backup is a separate saved copy; a restore uses that copy to recover something. The four rows keep different kinds of information separate. This is not a copy of the entire disk.

Choose this rowTo keep this information

 BlockchainYour existing blockchain data, so another Node can continue without downloading the same history again. No wallets or network passwords.

 Watch-only walletsYour public wallet information, names, labels and transaction records. No signing keys.

 Bitcoin Core configurationSupported Core preferences, such as storage/cache and selected interface choices.

 Node configurationSupported saved networks and passwords, managed VPN, time and desktop settings. This already includes the portable Core preferences.

Export finishes after copying and saving

All four Backup and Restore categories now finish after the backup is prepared, written and flushed to the destination. There is no second pass that reads the saved USB data back, decrypts a newly encrypted export to test it, or opens the outgoing watch-only collection in another Core process. A successful message means the copy/write operation completed, not that a recovery test was performed.

Core still stops cleanly for a consistent blockchain copy. The tools still refuse unsafe paths, incomplete reads, failed writes, insufficient space and unsupported input. Checksums are calculated as data are already being copied or packaged, without another USB read pass. File formats remain compatible with existing backups. Restore checks remain enabled before existing data or settings are changed; GPG authentication is not disabled.

Keep at least two separate copies of important backups and periodically test recovery on another installation. A latent media fault may first be noticed on restore without export read-back testing. Wait for the saved confirmation and eject/unmount properly; flushing pending writes can still take time on a slow drive and is not a verification pass.

Choose whether to encrypt the backup

Encrypt backup (optional) starts unchecked for wallet collections and configuration backups. An unencrypted file ends in .json; a GPG-encrypted one ends in .gpg. JSON is structured text data, not encryption. With encryption selected, enter the same nonempty passphrase twice. The tool accepts even one character, but that is not a sensible way to protect valuable private information. A random passphrase from KeePassXC is much harder to guess. An encryption error never quietly saves plaintext instead.

Privacy matters: a plain Node configuration may contain Wi-Fi passwords and VPN private keys. A public wallet can reveal addresses and balances. Keep these backups private and restore only a copy you trust. A checksum is a file fingerprint used to detect damage or a bad copy; by itself it cannot prove who created the file or that a stranger's replacement is trustworthy.

Find your USB

The file chooser lists USB / External media on the left. Connect the drive, or use Refresh USB. Click it to open it; if needed, the tool first mounts it, which means making its files available. Configuration and wallet collections use a .json/.gpg file. Blockchain restore uses a whole completed backup folder or the USB root with Use latest backup. A read-only drive can supply a restore but cannot receive a new backup. Choosing a file does not immediately apply it: review and confirmation still follow.

Continue using Settings while copying

Settings, the backup menu and the progress windows are independent. Minimize a window or switch with the bottom taskbar. Closing or minimizing a busy progress window does not cancel its work. Use Cancel operation when offered. You can export Node and Core settings while blockchain data is being copied. A watch-only transfer needs running Core, so finish the blockchain copy and start Core manually first.

Move to a new computer

Back up Node configuration and supported watch-only wallets to USB. Add a blockchain backup if you want to reuse the downloaded history.

Install a compatible Node on the other computer. Installation erases its selected disk.

Restore Node configuration, review it and restart to apply it.

Restore the blockchain copy, if you made one.

Start Core, restore the watch-only collection, compare addresses and labels, and let any necessary scan finish.

Keep the old copies until the new setup works. Offline Vault and its signing-wallet backups remain a separate responsibility. Showing a balance on Node does not prove that you can restore the signing wallet.

Backup and Restore on Home

After the first saved customization or use—such as connecting Wi-Fi, changing time zone/mouse settings, starting Core or importing a wallet—a second Backup and Restore shortcut appears on Home, after Private Workspace and before Encrypt Files. Settings keeps its entry. Both open the same menu and existing work. The Home shortcut stays after restart or after Core stops; it does not make a backup automatically or certify that an old backup is current.

Blockchain backup

Use Settings → Backup and Restore → Blockchain to reuse downloaded and validated chain data on another Node, or to avoid repeating that work after a disk replacement. Chainstate is the current unspent-output database; this feature also copies the related retained blocks, block index, undo/XOR information and supported indexes. It is not just a loose copy of the chainstate folder.

Create a backup

Connect an external drive with enough free space for the retained data. Choose Blockchain → Backup and the destination through USB / External Drive… or the folder selector.

Check I understand that Core will stop while the backup is created. and choose Create backup.

Core stops cleanly and finishes writing its databases. The tool copies the files once, calculating their restore checksums as those bytes pass through the copy.

Wait for Blockchain backup saved. There is no separate read-back verification stage. Core remains stopped: open Bitcoin Core manually when ready.

Finish other writes, eject/unmount the drive and keep the completed folder intact, including its manifest. Make another copy on different media as needed.

Each run creates a new complete snapshot of the retained data, not an incremental update. Earlier completed folders remain, so the drive needs space for another full copy. Cancelling or a failed write does not publish a partial folder as the latest completed backup. FAT32 cannot hold an individual file of 4 GiB or more; use a suitable filesystem such as exFAT, ext4 or NTFS when necessary.

What it does not contain

No wallet databases, private keys, Wi-Fi passwords or full system configuration are included. Use the separate backup rows for public wallets and settings. Pruned blocks that have already been deleted cannot appear in the snapshot. A blockchain backup does not recover signing keys and is not a guarantee that an old wallet can rescan all its history.

Restore a trusted copy

Use a compatible Node with the same Core version and Bitcoin network. Keep the source drive connected.

Open Blockchain → Restore. Select the USB root and Use latest backup, or choose the specific completed bitcoin-chain folder.

Review and confirm. Core stops during import. The restore copies into a separate candidate area, checks the file checksums and opens the candidate databases with an isolated Core process.

Allow room for the incoming copy beside the current chain. Existing chain data is not replaced until those checks succeed; wallet data is not part of that replacement.

Start Core if necessary. It continues from the saved tip and validates newer blocks. Restore restarts a Core that had been running before import; backup export never starts it automatically.

Import can therefore still have verification stages. The change is to backup export, not to safeguards for applying data from removable media. A checksum detects damage but does not prove that a stranger's chain snapshot is trustworthy; use your own trusted source. Arbitrary UTXO dump files are not accepted by this workflow.

You can minimize the copy window and continue using Settings, including exporting Node/Core configuration. Watch-only backup needs running Core and must wait. Avoid forcing shutdown, unplugging media or trying to start Core while its blockchain files are being copied.

Watch-only backups

Settings → Backup and Restore → Watch-only wallets saves a collection of supported public wallets from this Node. It is useful for moving addresses, labels and history to another Node. It deliberately excludes signing wallets and private keys.

Make a collection

Start Core and finish any blockchain-copy operation.

Choose Backup and a destination folder. Turn on optional encryption if you need it.

Choose Create wallet backup. The tool identifies supported watch-only wallets and asks Core to make a consistent native public-only export.

Read the result, including any skipped-wallet count, and keep the saved .json or .gpg file private.

A wallet that was closed may be loaded briefly for inspection and then put back in its previous state. The collection keeps public descriptors, receiving/change-address state, labels, address-book entries and transaction records. Descriptors are the wallet's address instructions. The collection cannot authorize spending and cannot replace your original offline signing wallet.

The export is packaged, optionally encrypted, written and flushed to the destination. It is not reopened in a second Core process and is not read back from USB before the saved confirmation. This avoids the extra export verification step; Core's native public-only export is still used rather than copying an active wallet database.

Restore it

Use the same Core version and Bitcoin network, and start Core on the target Node.

Choose Restore in the Watch-only wallets row. Select the collection file; supply its passphrase only if it is encrypted.

Choose Review backup, check the wallet names, approve the review, then choose Restore wallets.

If a name already exists, a new restored name is used rather than overwriting the existing wallet. Repeating this backup's restore does not duplicate wallets already restored successfully.

Compare addresses and labels in Core and let any needed scan finish.

A multi-wallet restore can succeed partly: wallets already completed remain if a later one fails. Repeating the restore can continue the work. Limits are 32 wallets, 32 MiB for one public export and 64 MiB combined, also limited by free private RAM. MiB is a storage-size unit; those limits keep the temporary in-memory work bounded.

A pruned chain cannot provide old blocks it no longer has. Public exports also cannot recreate missing hardened address derivations that require private-key information: please keep the original Vault and review any address/scan warning.

A single watch-only.dat exported straight from Vault is different from this collection. Open that file with Bitcoin Core → File → Restore Wallet. This menu expects Node's .json/.gpg collection format.

Core configuration

Configuration means settings, not your money or transaction history. Use Settings → Backup and Restore → Bitcoin Core configuration to transfer supported Core preferences without copying the operating system's network settings.

What is included?

Examples include the pruning limit; database cache, which is memory used to speed up data access; the number of verification threads, which are workers checking data; limits for pending transactions; maximum peer connections; and the upload target. Selected Core interface preferences include Coin Control, which lets you choose which available coins to spend, and the PSBT controls.

Only recognized, validated options are copied. This is not an unchecked copy of every line in bitcoin.conf, Core's manual configuration file.

Save and restore

Choose Backup, select a USB folder and choose whether to encrypt.

Choose Save backup and wait for the saved confirmation; there is no read-back verification pass.

On the target Node choose Restore, select the file and choose Review backup.

Read the settings, approve them and choose Restore on next restart.

Restart normally, then check Core's settings.

Wallets, wallet registrations, blocks, network credentials, source-computer data paths and commands/scripts are excluded. Unsupported options are not silently copied. A Node configuration backup already includes this portable Core subset, so a separate Core backup is optional when you also save Node configuration.

Restoring a smaller pruning target can later remove older blocks. Restoring a setting does not bring back block files that are missing.

Node configuration

This backup is a shortcut for setting up another Node the way you like it. Open Settings → Backup and Restore → Node configuration. A snapshot here means a saved selection of your current settings, not a complete copy of the computer's disk.

What it keeps

It can keep supported saved Wi-Fi networks and their stored passwords, Ethernet profiles, the managed WireGuard VPN and privacy choice, time zone and automatic-time choice, keyboard layout, display scale, mouse speed for matching device names and supported Core preferences. New backups also keep Keyboard and Mouse repeat/Num Lock choices and supported mouse/touchpad options. Restore these newer backups on a Node with this feature; older Node versions may reject the new format. This Node still reads earlier configuration backups.

A network profile is the saved information needed to connect. Display scale controls how large interface elements look. The backup does not save an old clock reading to set the computer back to that time later.

Create the copy

Finish applying the settings you want to keep and connect a USB drive.

Choose Backup → Choose folder… and select the drive or a folder on it.

Leave Encrypt backup (optional) off for a plain .json file, or turn it on and enter the same passphrase twice.

Choose Save backup or Save encrypted backup. Wait for the saved confirmation and note the filename. There is no read-back verification pass.

A plain Node backup can expose saved Wi-Fi passwords and VPN private keys. Keep it private. Encryption protects the saved file, not the running computer. Please do not store the only copy of the passphrase inside the file that needs that passphrase to open.

Apply it to another Node

Open the same category and choose Restore.

Select the .json or .gpg file. Only an encrypted file needs its backup passphrase.

Choose Review backup. Check the time zone, network counts, privacy profile and any omissions.

Tick I trust this backup and approve the settings shown above, then choose Restore on next restart.

Restart normally. The checked settings are applied before networking starts. Check pending restore shows the staged request or its result; Cancel pending restore cancels an unapplied request before restart.

What does not move

The restore keeps local wallets and network profiles found only on the target computer. It does not clone login passwords/accounts, disk encryption, disk identifiers, Bluetooth pairing keys, arbitrary scripts, external certificates or unsupported VPN plug-ins. Pair Bluetooth devices again on a different adapter. Mouse settings apply only when the device name matches, and only to capabilities that device offers.

Only passwords actually stored in supported profiles can be transferred. Some workplace authentication tools store credentials elsewhere; missing passwords are not invented. Unsupported values and omissions are reported for you to review.

If the old and new computers will be online together, they may need different manually assigned IP addresses and different WireGuard peers. Reusing the same address or tunnel identity can cause a conflict.

This contains no blockchain or wallet database. Use those separate backup rows. You do not normally need a separate Core configuration backup because Node configuration already includes the supported Core settings.

Networking

Connect to Wi-Fi or a cable

Click the Network Status icon just to the left of Restart. Choose your Wi-Fi network, enter its password and click Connect. Saved networks can reconnect automatically. Ethernet is a wired connection: connect the cable and the system normally sets it up automatically.

Advanced settings is for hidden Wi-Fi names, workplace networks and manually assigned IP addresses. An IP address is the network address used to reach a computer. You usually do not need to set one manually on a home router. A connection to the router is not proof that the Internet is reachable.

If you open Core without a connection, Node offers network setup first. Use Core offline still lets you inspect local data. Changing Wi-Fi does not remove your chosen network protection rules.

Choose a privacy connection deliberately

Open Settings → Bitcoin Core Network & Privacy. These choices affect how information leaves the computer; they do not make an unsafe computer safe.

ChoiceWhat it does

ClearnetCore connects directly to Bitcoin peers. They see your public IP address; your Internet provider may recognize Bitcoin traffic.

TorCore's peer-to-peer traffic goes through the local Tor service rather than directly to peers. The operating system's other traffic, including software updates, still uses its ordinary connection.

WireGuard VPNThe computer routes traffic through the configured encrypted VPN tunnel. Its protection rules block ordinary fallback outside that tunnel, apart from reaching the VPN server and essential connection setup. The VPN provider becomes someone you must trust.

A firewall is a set of rules allowing or blocking network traffic. The VPN's kill switch means these rules block fallback if the tunnel stops. DNS is the service that translates website names into network addresses. This Node's managed WireGuard setup protects against unintended traffic outside its tunnel, including ordinary DNS and IPv6 traffic. Neither Tor nor a VPN guarantees anonymity.

Import a supported full-tunnel WireGuard configuration from your provider or own server. It must have a numeric server address and explicit DNS settings. Configurations containing scripts or unsupported split routes are refused. Tunnel private keys are stored in protected system files. A split route sends only some traffic through the VPN; this tool is designed for the supported whole-device configuration instead.

Changing the privacy profile first stops a running Core, checks and replaces the network policy, then restarts it. If it was already stopped, it stays stopped. If the change fails, Core remains stopped rather than silently using a less-private route. I2P setup and Tor bridges are not exposed in this interface.

Sending a transaction privately is a separate option

Private transaction broadcast concerns the initial sending of a transaction, not every connection Core makes. It uses Core 32.1's private-broadcast route. The underlying feature can use short-lived Tor/I2P connections; this Node exposes the Tor configuration. The submitted transaction is not initially added to the local mempool by this route.

Turning on Tor for this purpose also makes Tor available for ordinary peer selection. A failed private route must not silently fall back to standard sending. A returned transaction ID is a reference number, not proof that peers received the transaction or that a block confirmed it. Please check transaction status afterward.

Connect a Bluetooth keyboard or mouse

Open Settings → Bluetooth Devices or press Ctrl+Alt+B. Switch on the adapter, put the device into pairing mode, then choose Search, pair and connect. For a keyboard, type the displayed pairing code on that keyboard and press Enter when asked. Mark a device you own as trusted to help it reconnect.

Pairing means the two devices remember each other. The installed Node saves those pairing details. After restart, wake or switch on the device. Pairing done only in the installation session must be repeated after installation. A wired or built-in keyboard and mouse are useful during setup; Ctrl+Alt+B also works in the installer. Bluetooth file transfer and network sharing are not enabled by this Node setup.

If no Bluetooth adapter appears, please check any airplane-mode switch and the computer's firmware settings. Common adapter firmware is included, but some devices need different firmware or a compatible USB adapter.

Keyboard and Mouse

Open Settings → Keyboard and Mouse. On the Keyboard tab, choose the keyboard model, layout/language and variant. A layout says which character each key types; a variant is an alternative arrangement. Leave the variant on Default unless you need another one. You can enable or disable held-key repetition, set the delay and repetition rate, and choose whether Num Lock starts on. Use the test area after Apply and Save; please do not type passwords there.

The chosen layout applies to your current desktop and to the login screen after restart. Repeat and Num Lock preferences are applied when the desktop starts. They do not replace an older encrypted installation's disk-unlock keyboard configuration.

On Mouse and Touchpad, select a connected device and adjust pointer speed. Depending on its capabilities, you can swap the main button for left-handed use, reverse scrolling with Natural scrolling, enable tapping, ignore touchpad movement while typing, emulate a middle click, and choose movement/scroll methods. Greyed-out options simply are not offered by that device. Adaptive movement speeds up with your hand; Flat uses a steady relationship. Settings are remembered for matching device names and reapplied after reconnect or restart. They do not change Core or reconnect Bluetooth by themselves.

Status & diagnostics

Open Settings → Bitcoin Core Status for a live overview of this computer's Core. It reads information locally; it does not ask a public website to tell you what your node is doing.

What the cards mean

Version identifies the Core program you are running. Blocks are the blocks Core has checked. Headers are the block summaries it knows about. Peers are other Bitcoin computers it is connected to. Mempool means the transactions your node knows about that are waiting to be included in a block. Network distinguishes real Bitcoin, called mainnet, from testing networks. The privacy profile tells you whether the Node uses direct connections, Tor or the configured VPN.

The storage figure is space on the actual blockchain filesystem—the storage area on its disk—not necessarily every disk attached to the computer. Values refresh automatically. When Core is stopped or cannot be reached, the dashboard says so rather than displaying a made-up success.

Open details without crowding the dashboard

Show technical details opens its own window. You can resize or minimize it while keeping the main dashboard tidy. The information is grouped by blockchain, network/software, pending transactions, peer connections and wallet scanning when available.

Use Find a field or value… to look for a particular item. Expand all opens the groups; Collapse all closes them. Refresh takes a new snapshot—a copy of the current readings—so the list does not keep moving while you read. The Raw JSON tab shows the same information in a structured text format mainly useful for technical support.

Copy snapshot copies it to the clipboard, not to a server. Please review it before sharing: wallet names and other details can reveal private information. Closing this window does not stop Core.

A connected Core can keep synchronizing even if a separate software-download server is unavailable. The Updates chapter explains how to distinguish those situations.

Encrypt & Decrypt Files

Encrypt means protect a file with a passphrase. Decrypt means recover its contents with that passphrase. These tools use GnuPG, usually called GPG. They do not encrypt the whole installed operating system or turn an online Node into an offline signer.

This separate general file-encryption tool retains its recovery checks. The copy-only change applies to the four categories in Backup and Restore, not to this utility or to authenticated decryption.

First make a proper wallet backup

If the file is a wallet, use Bitcoin Core → File → Backup Wallet to save a consistent database in Private Workspace. A database is a structured file Core works with. Copying its live file while Core is changing it can produce an unusable copy; the built-in Backup Wallet command avoids that problem.

Open Encrypt Files on Home and select the saved file.

Choose a new .gpg destination on USB or persistent storage.

Enter and repeat a passphrase. Extra independent layers are optional. Each layer is another encryption step with its own passphrase; all required passphrases must be available for recovery.

Wait for verification to finish, then keep separate copies and store their required passphrases separately. Originals are not overwritten.

A verified single Core SQLite wallet.dat is encrypted directly. Other files or folders may first be packed into a TAR archive, which keeps names and folders together but is not itself encryption. The output uses interoperable OpenPGP AES-256 CFB+MDC: AES protects the contents, and the integrity check helps detect damaged or altered encrypted data. The tool checks each layer and complete recovery before publishing the final file.

Open an encrypted file

Choose Decrypt Files and select the .gpg file.

Enter the needed passphrases. For layered Node/Vault files, their order does not matter to the recovery tool. For a normal single-layer AES-256 GPG file made elsewhere, choose Recover one ordinary GPG layer only.

Wait for decryption and its integrity check. The recovered contents are placed in a new folder inside Private Workspace, not directly on the source USB.

Files opens Private Workspace automatically after successful decryption, showing the recovery folder without another success confirmation. Wrong passphrases, failed checks and cancellation do not open the folder as if recovery succeeded. Recovered files remain in RAM until you deliberately save or restore them elsewhere. No partial recovered plaintext is published after a failed or cancelled operation.

To restore a public wallet file, use Bitcoin Core → File → Restore Wallet and select the recovered database. Core creates a persistent wallet on its installed disk; the active restored wallet is no longer just a RAM file. Check addresses and labels, wait for validation/scanning and resolve pruned-history warnings. In the Node/Vault setup, keep signing-wallet recovery on offline Vault, not this online computer. Practise recovery periodically, including on another trusted machine.

Use the USB sidebar

The input selectors and encrypted-file destination selector show Places and USB / External media. Click a listed drive to open or mount it. Refresh USB checks again without formatting anything. A read-only drive can be an input, not an output. Open and unlock encrypted media in Files first, then refresh.

Files shows Core, Private Workspace and PSBT Transfer Folder in its widened sidebar. Core's data view is read-only; use Core's own commands to change wallets. Saving encrypted output to USB is different from decryption: decrypted output always goes to RAM first. Use Files to copy a recovered file elsewhere only deliberately.

Persistent storage

Persistent means “still there after restarting.” The installed Node keeps its blockchain, chainstate, wallets and ordinary settings on disk. Its two temporary working folders are different:

PlaceAfter shutdown or restart

Core data and ordinary files saved on diskKept on disk.

Private WorkspaceCleared: recovered files and temporary work live in RAM.

PSBT Transfer FolderCleared: public wallet/PSBT transfer files live in RAM.

A file copied to USBKept on that USB, if saving finished successfully.

Three Places in Files

Files opens Core, a read-only view containing wallet folders, blocks, chainstate and logs. The left-hand Places list is Core, Private Workspace, PSBT Transfer Folder; connected drives appear under Devices. The default width is wide enough for names, and a wider manual choice is preserved.

Private Workspace and PSBT Transfer Folder are separate shared RAM locations available to the desktop and Core. Closing a window does not clear them; restarting or losing power does. Ordinary suspend leaves RAM powered and is not a way to clear the workspace. The old disk-based Public Wallet Transfer folder is not automatically erased; any old files left there remain persistent.

Before encryption/decryption, Node verifies that the private workspace really is on its dedicated RAM filesystem. If that check fails, it stops rather than silently writing plaintext to disk. Node disables swap and hibernation; swap is disk space an operating system might otherwise use to hold memory pages. The workspace is limited by available memory, so please keep temporary files small while Core is busy.

Copying outside RAM makes that new copy persistent. Restoring a wallet into Core also makes a persistent copy. Encrypting a backup does not erase or protect its original file or the active wallet database.

USB access and safe removal

Node's backup and file tools, Core, KeePassXC, Editor and Files show removable media in their file sidebars. Node's own choosers refresh live and provide Refresh USB. If a USB is connected while Core's or KeePassXC's chooser is already open, reopen the chooser or select USB Media.

Core can read and write through its checked USB view—for example a wallet backup or PSBT—without receiving write access to the rest of the operating system. Existing USB files keep their permissions; new Core exports belong to the desktop account on filesystems that support owners. A protected/read-only drive remains read-only. Unlock an encrypted drive in Files before using it in another program.

For removal, finish saving and close files on that drive. Core's USB view can keep it busy while Core is open, so please stop Core normally, then use Files → Eject/Unmount. Eject asks the system to finish writes and release the drive. If another application still has a file open, close it and retry. Do not pull out the drive while copying. Reconnecting creates a fresh checked view, not a stale path to the old device.

End a session

If both RAM folders are empty, Restart and Shut Down show the ordinary confirmation. If either contains anything, including a hidden file or empty folder, two warnings are followed by a five-minute countdown. Cancel, Esc or closing that window keeps the session open. Restart now or Shut down now skips the remaining wait. Core stops carefully only when the countdown finishes or the immediate action is chosen.

Please finish or cancel an open encryption job first and copy any RAM files you need. Shutdown warnings do not verify your backups. A sudden power loss also loses RAM contents. RAM-only storage limits leftovers on disk; it does not protect files from an already compromised running system or promise instant physical memory sanitization.

KeePassXC and time settings

KeePassXC opens its passphrase generator with six random EFF-list words as a starting choice. Choose a suitable length and generate each secret independently. You do not need a password database to use the generator. Its temporary profile/cache are in RAM; changes survive reopening during this session but reset after boot. Automatic clipboard clearing starts off. Enable it in Tools → Settings → Security if preferred. Save a password database you need to keep on USB or persistent storage, not only in RAM.

Click the clock or use Settings → Date & Time. Choose your time zone, such as Europe/Zagreb, and automatic network time. Turn automatic time off to enter a date/time manually. Apply and Save preserves the settings after restart. Automatic time may wait for a reachable time server. In Tor peer mode, time synchronization uses ordinary operating-system networking; in WireGuard mode it follows the VPN policy. Manual time works offline.

Updates

Open Settings → Software Updates to check what is available before installing anything. Updates for Debian and applications are separate from changing Bitcoin Core's version. Checking does not automatically replace your software.

Debian and KeePassXC

Choose the system update check and read the proposed package versions. A package is an application or system component prepared for installation. Debian packages come through Debian's signed archive; the separately supplied KeePassXC package has its release signature verified. A signature is a cryptographic check against a trusted publisher's key, not just a matching filename.

Installation needs your explicit confirmation but not another login-password prompt in the active Node desktop. The progress display shows actual package steps. These updates do not deliberately stop/restart Core, although a package may restart another system service. A message indicates when restarting the computer is required or may be needed, for example after a new kernel—the core of the operating system.

Updates use operating-system networking: ordinary direct Internet access when the Bitcoin peer profile is Tor, or the enforced VPN in WireGuard mode. The selected privacy policy is retained.

Change Bitcoin Core only after review

The update page shows the active verified Core version and can check the official stable-release record. Choose a supported Core 32 release and Download and verify Core release. Please read the version, file hashes and signing-key fingerprints before approving installation. A fingerprint identifies the full signing key.

The archive must match official signed checksums with at least two distinct currently valid signers from the bundled trusted key set. Expired signers do not count. Downgrades and a new major version are refused; moving to a new major Core version needs a reviewed Node system update.

Activation stops Core cleanly, makes a protected local snapshot of wallet databases/settings and installs the verified program in a separate directory. Old binaries remain available. A stopped Core stays stopped; open it when ready. Startup checks the selected Core program hash. A failed health check leaves Core stopped. Database formats can change, so the system does not automatically roll wallet data backward. Keep an independent backup on another device: the local maintenance snapshot is not that backup.

Why an update check can fail while Core still syncs

Different services use different servers. KeePassXC release lookup first contacts the project's official GitHub API, a machine-readable release listing. If that is unavailable or rate-limited, Node can use the official KeePassXC download page instead. It shows which source it used. Secure connection checks and package signature verification remain enabled.

HTTP 503 means a server or gateway reported temporary unavailability. It is not automatically a Wi-Fi or clock error. DNS errors concern finding the server address; timeouts mean no answer arrived in time; TLS/certificate errors concern the secure connection; local write errors concern saving files on this computer. Changing your time zone only changes the displayed time. A wrong actual date/time can affect secure certificates, but do not reset a correct clock merely because a server returns 503.

If both official sources fail, the check stays incomplete. Debian results already found remain visible, but installation is disabled until a fresh complete check succeeds. Old metadata does not trigger a downgrade or a false “up to date” result.

Use normal restart/shutdown and keep free space. If Core reports database corruption, stop and preserve the data before investigating. There is no automatic wallet deletion, repair or fallback to a less-private network.

Troubleshooting

Start with the message shown by the application. Please do not delete files, reset the clock or change privacy settings merely to make a warning disappear.

What you seeWhat to do

Core is stopped after bootThis can be normal: open Bitcoin Core to start it. If it fails, check that its selected data disk is connected, then use Bitcoin Core Status for the actual error.

Sync percentage stays low while headers increaseHeaders are the small summaries checked early in download. Watch the header count and peer connections; the meter does not promise a finish time.

A wallet balance is zero or provisionalLet blockchain checking and wallet scanning finish. If old blocks were pruned, recover the required history. Do not pretend an old wallet was created later to bypass the warning.

A PSBT will not openCheck that you selected the intended file in Core. Independently review recipients, amount, fee and change before signing or broadcasting.

Private broadcast is not visibleCheck Tor and transaction status. A transaction ID does not prove successful relay. Do not silently switch to a standard route.

Save seems inactiveSelect an output folder. If encryption is on, enter and repeat the passphrase. Read the visible feedback below the controls.

Backup no longer shows a verification stageThis is intentional for all four backup exports. Wait for writes to finish, keep multiple copies and test recovery separately. Restore still validates its input.

Core stays stopped after blockchain backupThis is intentional. Open Core manually after the operation finishes.

Watch-only backup is blocked during chain copyingWallet transfer needs running Core. Finish the chain job, start Core, then retry.

Technical diagnostics are available in the separate details window and in Terminal. Terminal accepts advanced system and Core commands; do not paste commands you do not understand. Please inspect logs/screenshots before sharing them: public wallet data and device/network details may still be private.
